.claude の中に何があるか

仕込みの置き場は .claude の中にある

~/.claude/ ← ホーム側｜自分の全プロジェクトに効く

├── CLAUDE.md 毎回読まれる指示書き（自分の好み）

└── settings.json 権限と設定

 

your-project/

└── .claude/ ← プロジェクト側｜git でチームに共有できる

    ├── CLAUDE.md このプロジェクトの決まりごと

    ├── rules/ パスを限った規則

    ├── skills/ 手順のパッケージ

    └── settings.json 権限と止めどころ

つまり、置き場所は二系統。自分の好みはホーム側へ、チームで共有する決まりごとはプロジェクト側へ。区別を誤ると、
個人的な好みが他の人の環境にも効いてしまう。全部を最初に作る必要はない。

CLAUDE.md に何を書くか

毎回説明し直すことを書いておく

書く

  • 手順 — テストは npm test で走らせる
  • 置き場所 — API のコードは src/api に置く
  • 決まりごと — コミットメッセージは日本語で

書かない（別の場所へ）

  • 何段階もある手順 → skills へ
  • 一部のファイルにだけ関わる規則 → rules へ
  • 分量そのもの — 目安は1ファイル200行以内

書きどきは、同じ説明を二度目に打ち込んだとき。書き方は検証できる具体性で。「きれいに整形する」
ではなく「インデントは半角2つ」、「テストして」ではなく「コミット前に npm test を走らせる」。
曖昧な指示は曖昧にしか守られない。

settings.json — 権限と止めどころ

触れる範囲と止めどころを設定で決める

CLAUDE.md ＝ お願い

  • 文脈として伝わるだけ
  • 守られないことは起こり得る
  • 書きすぎると、かえって守られにくい

settings.json ＝ 宣言

  • ツールを使う前に許可ルールと突き合わせる
  • どのツールをどこまで使ってよいかを決める
  • 読み取りは通す、消す操作は必ず確認

つまり、絶対に触られたくない場所があるなら、お願いではなく設定に書く。使い分けだけ覚えて帰ればよい。
設定ファイルの書き方は持ち帰り資料に載せる。

hooks の三階層（イベント → 対象 → 処理）

決まった場面で、決めた処理を自動で走らせる

{ "PreToolUse": [ ← ① イベント｜どの場面で

つまり、規律で守るを、仕組みで守るに変える道具。書き方まで今日覚える必要はない。

つまり — 回して寄せる

先に決めるのは、直す物差しを持つため

✗ 一発で当てるため

  • 最初に全部決めて一直線に完成させる、
    ではない
  • 途中で違ったと分かることは必ずある
  • 早めに出して、見て、直すほうがうまくいく

○ 直す物差しを持つため

  • 何を作るか・何ができたら完成かが決まれば
  • 出てきたものが狙いに近いか遠いか判断できる
  • 物差しがないと、直すつもりが迷走になる

先に決めるのは三行で足りる。分厚くすると、今度は仕様書を書くこと自体が目的になる。回し方の技術は、
四段階のうち段階④から次の一周へ戻るところの設計にあたる。
